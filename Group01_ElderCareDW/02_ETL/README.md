# 02_ETL — ไปป์ไลน์สร้างคลังข้อมูล

> **สถานะ:** Dimension ทั้ง 6 ตารางเสร็จและตรวจผ่านแล้ว · **ตาราง Fact ยังไม่ได้ทำ**

## วิธีรัน

```bash
python -m pip install -r requirements.txt

python fetch_snapshots.py --dates 2019-01-17 2026-06-24 2026-07-29 2026-08-06
python run_dims.py          # สร้าง dimension แล้วเขียนลง 03_Data_Warehouse/eldercare.duckdb
python verify_dims.py       # ตรวจผลด้วยคำถามที่รู้คำตอบอยู่ก่อน
```

คำสั่งอื่นของขั้น Extract

```bash
python fetch_snapshots.py --list         # ดูรายการ 88 งวด พร้อมขนาดไฟล์
python fetch_snapshots.py --quarterly    # โหลดรายไตรมาส (~30 งวด) ค่าเริ่มต้น
python fetch_snapshots.py --all          # ครบทุกงวด ~1 GB
python run_dims.py --dates 2026-06-24 2026-07-29
```

รันซ้ำได้เสมอ: งวดที่โหลดแล้วจะถูกข้าม และ dimension ถูกสร้างใหม่ทั้งตารางทุกครั้ง
จึงไม่มีสถานะค้างจากการรันครั้งก่อน

## ภาษาที่ใช้ในโฟลเดอร์นี้

**โค้ดและข้อมูลเป็นภาษาอังกฤษทั้งหมด** — คอมเมนต์ docstring ข้อความที่ print
ข้อความในตารางบันทึกการทำงาน และ **ค่าที่เก็บใน dimension** (`For profit`, `Unknown`,
`Medium (50-99 beds)`, `Urban`, `Post-COVID`) ส่วนเอกสาร `.md` และเอกสารออกแบบยังเป็นภาษาไทย

ข้อยกเว้นเดียวคือคอลัมน์ `month_name_th` ใน `Dim_Date` ที่ยังเก็บชื่อเดือนภาษาไทย
เพราะชื่อคอลัมน์ระบุไว้แบบนั้นในเอกสารออกแบบ และมีไว้เป็นป้ายกำกับบนแดชบอร์ดภาษาไทยโดยตรง

## การตัดสินใจที่ต้องรู้ก่อนแก้โค้ดนี้

**ทุก dimension มีแถว `key = -1` (`Unknown`)** — เอกสารออกแบบระบุไว้เฉพาะ `Dim_Date`
แต่ที่นี่ทำให้ครบทุกตาราง เพื่อให้ตาราง Fact ไม่ต้องปล่อยคีย์นอกเป็นค่าว่าง
(คีย์นอกที่ว่างทำให้แถวหายตอน join แบบเงียบ ๆ)

**`Dim_Chain` แยก `Independent (no chain)` (`chain_key = 0`) ออกจาก `Unknown` (`-1`)** —
สถานที่ในงวดปี 2562 ต้องชี้มาที่ `Unknown` เพราะยุคนั้นไม่มีคอลัมน์เครือเลย
ต่างจากสถานที่ในงวดปี 2569 ที่คอลัมน์ว่างจริง ซึ่งแปลว่ารู้แน่ว่าไม่สังกัดเครือ

**แกนเวลาของ SCD2 คือ `Processing Date` ในไฟล์ ไม่ใช่วันที่ของ ZIP บนเซิร์ฟเวอร์** —
สองค่านี้ไม่ตรงกัน (ZIP ของวันที่ 2026-06-24 มี Processing Date เป็น 2026-06-01)
เลือก Processing Date เพราะภาคผนวกของเอกสารออกแบบจับคู่คอลัมน์นี้ไว้กับ `snapshot_date_key`
ตาราง Fact จึงต้องใช้แกนเดียวกัน ไม่งั้นเงื่อนไข
`effective_date <= วันที่ของ fact < expiry_date` จะหาเวอร์ชันไม่เจอ

**การเทียบใน SCD2 เทียบเฉพาะคอลัมน์ที่รู้ค่าทั้งสองฝั่ง** — ถ้าเดิมไม่รู้ค่าแล้วงวดใหม่รู้
(เช่น `abuse_icon` ที่เพิ่งมีหลังปี 2562) จะเติมลงเวอร์ชันที่เปิดอยู่ ไม่เปิดเวอร์ชันใหม่
เพราะ "จากไม่รู้เป็นรู้" คือข้อมูลมาช้า ไม่ใช่สถานที่เปลี่ยนสถานะ
ถ้าไม่ทำแบบนี้ ตอนข้ามยุค 2562 → 2569 จะเกิดเวอร์ชันปลอมพร้อมกัน **ทุกแห่ง** (14,300 แห่ง)

**ชื่อสถานพยาบาลถูกปรับเป็นตัวพิมพ์ใหญ่ทั้งหมด** (กฎ Q5) เพราะยุค 2562 สะกดตัวพิมพ์ไม่คงที่
ถ้าไม่ปรับ ชื่อเดิมที่เขียนคนละตัวพิมพ์จะถูกนับเป็น "เปลี่ยนชื่อ" ราว 17% ของทุกแห่ง

## สิ่งที่ยังค้าง

1. **`pop_65plus` ใน `Dim_Geography` ยังว่างทั้งคอลัมน์** — ต้องมี Census API key
   หรือใช้ทางถอยแบบ CSV นิ่ง **BQ1 ยังตอบไม่ได้จนกว่าจะเติมช่องนี้**
2. **ตาราง Fact ทั้งสองยังไม่ได้ทำ** — กฎ Q2 (กำจัดซ้ำสองระบบตามยุคของ `Fine ID`),
   Q4 (`is_suspect`) และ Q8 (หน่วยของอัตราลาออก) จึงยังไม่ถูกเขียนเป็นโค้ด
3. **ข้อสังเกตที่กระทบ Fact 1 โดยตรง** — งวด `2026-07-29` กับ `2026-08-06`
   มี `Processing Date` เท่ากันคือ `2026-07-01` และมีจำนวนแถวเท่ากันคือ 14,693 แถว
   (งวดหลังคือการเผยแพร่ซ้ำ) ถ้า `snapshot_date_key` มาจาก Processing Date
   คีย์หลัก `(snapshot_date_key, ccn)` ของ Fact 1 จะซ้ำทันทีเมื่อโหลดสองงวดนี้พร้อมกัน
   ต้องตัดสินใจก่อนเขียน Fact ว่าจะกำจัดงวดที่เผยแพร่ซ้ำ หรือเปลี่ยนแกนเวลาไปใช้วันที่ของแฟ้ม
