### 2.1 สามแหล่ง และแหล่งที่ซับซ้อนกว่า CSV (0:45)

> โจทย์กำหนดอย่างน้อย 3 แหล่ง และอย่างน้อยหนึ่งแหล่งต้องซับซ้อนกว่าตาราง CSV ทั่วไป
>
> - **S1 — แฟ้ม ZIP รายงวดของ CMS** งวดละประมาณ 20 ไฟล์ เราใช้จริง 6 ไฟล์
>   โหลดมา **32 งวดรายไตรมาส ปี 2562–2569** นี่คือความซับซ้อนแบบ *หลายไฟล์หลายช่วงเวลา*
> - **S2 — Provider Data Catalog API** ตอบกลับเป็น **JSON** ใช้ไล่รายการงวดทั้งหมด
>   และดึงข้อมูลงวดปัจจุบันมาตรวจทานหลัง Load
> - **S4 — ข้อมูลประชากรอายุ 65 ปีขึ้นไป** จาก **Census ACS API** ซึ่งต้องใช้ API key
>   ถ้าไม่มีคีย์โค้ดจะสลับไปใช้ไฟล์ประมาณการของ Census เองอัตโนมัติ และบันทึกลง log ว่าใช้ทางไหน
>
> **จุดที่เสียเวลามากที่สุดคือ API ของ Census** — ถ้าไม่ใส่คีย์ เซิร์ฟเวอร์ตอบ
> HTTP 302 ไปหน้า missing key แล้ว body ว่าง **โดยไม่มี error** ถ้าไม่ตรวจก็จะได้ข้อมูลว่างมาเงียบ ๆ

### 2.2 ปัญหาคุณภาพข้อมูล (1:00)

> โจทย์กำหนดอย่างน้อย 3 ประเภท เราพบและจัดการ **8 ประเภท คือกฎ Q1–Q8**
> ขอยกสามข้อที่ *เกือบทำให้คำตอบผิดโดยไม่มีอะไรฟ้อง*
>
> **หนึ่ง — Mismatched Keys จากศูนย์นำหน้า** รหัสสถานพยาบาล CCN คือ `015009`
> ถ้าอ่านเป็นตัวเลขจะเหลือ `15009` แล้ว **join ไม่ติดแบบเงียบ ๆ** ไม่มี error
> มีแต่แถวที่หายไป → เราจึงอ่านทุกคอลัมน์เป็น string ก่อนเสมอ แล้วค่อยแปลงเฉพาะตัวที่เป็นตัวเลขจริง
>
> **สอง — ชื่อ Category ไม่สอดคล้องกัน** ยุคปี 2562 สะกดชื่อสถานพยาบาลตัวพิมพ์ไม่คงที่

>

> แล้วนับไว้ ไม่ส่งต่อไปให้ปฏิทินอีกแบบเงียบ ๆ · ถ้ามีสองรูปแบบอธิบายได้เท่ากันแต่ให้ผลต่างกัน

> ที่เป็นการระงับการจ่ายเงิน ถ้าทำตามจะได้ยอดที่นับซ้ำ 382 ล้านดอลลาร์
> เราจึงเปลี่ยนไปใช้คีย์ธรรมชาติบวกลำดับที่ภายในกลุ่ม **แล้วยืนยันด้วยการกระทบยอด
> กับตัวเลขของ CMS ที่ตรงกันครบ 6,563 แห่ง** — นี่คือมาตรฐานการตรวจที่เราใช้ทุกครั้ง
> **และสมาชิกทุกคนอธิบายโค้ดส่วนที่ตัวเองรับผิดชอบได้ทั้งหมด**
