### AI แนะนำอะไร

เขียนโค้ดให้ทั้งชุด แยกเป็น 8 ไฟล์ตามขั้นของไปป์ไลน์ (`config` → `fetch_snapshots` →
`columns` → `clean` → `dimensions` → `load` → `run_dims` → `verify_dims`)
ข้อเสนอเชิงออกแบบที่ไม่ได้อยู่ในเอกสารออกแบบเดิมมีสี่ข้อ

1. ให้ทุก dimension มีแถว `key = -1` สำหรับ "ไม่ทราบ" ไม่ใช่เฉพาะ `Dim_Date`
2. ให้ `Dim_Chain` แยกแถว "ไม่สังกัดเครือ" (`chain_key = 0`) ออกจาก "ไม่ทราบ" (`-1`)
   เพราะงวดปี 2562 ไม่มีคอลัมน์เครือเลย จึง *ไม่รู้* ต่างจากงวดปี 2569 ที่คอลัมน์ว่าง
   ซึ่งแปลว่า *รู้ว่าไม่สังกัด*
3. ใช้ `Processing Date` ในไฟล์เป็นแกนเวลาของ SCD2 ไม่ใช่วันที่ของ ZIP บนเซิร์ฟเวอร์
4. ตอนเทียบ SCD2 ให้เทียบเฉพาะคอลัมน์ที่รู้ค่าทั้งสองฝั่ง

### ตรวจสอบความถูกต้องอย่างไร

รัน `python verify_dims.py` ซึ่งเปิดฐานข้อมูลจริงแล้วถามด้วย SQL แยกจากโค้ดที่ใช้สร้าง
(ถ้าตรวจด้วยตรรกะเดียวกับที่ใช้สร้าง จะผ่านเสมอแม้ตรรกะนั้นผิด) ผลคือ **ผ่าน 22 ข้อ ตก 0 ข้อ**
ข้อที่มีน้ำหนักที่สุดสี่ข้อ

| ตรวจอะไร | วิธี | ผล |
|---|---|---|
| แถวทดสอบ CCN 015009 | อ่าน CSV งวด มิ.ย. 2569 แล้วหาร 52.4 / 57 | **91.93%** ตรงกับที่เอกสารระบุ (ไม่ใช่ 90.53% ของ API ซึ่งเป็นคนละงวด) |
| SCD2 ไม่มีช่วงเวลาทับกัน | `LAG(expiry_date) OVER (PARTITION BY ccn ...)` แล้วนับแถวที่ `effective_date < prev_expiry` | 0 แถว |
| ทุก CCN มีแถวปัจจุบันหนึ่งแถว | `GROUP BY ccn HAVING COUNT(*) <> 1` บนแถว `is_current` | ผิด 0 CCN |
| การเทียบ SCD2 แบบใหม่จำเป็นจริง | รันเทียบสองแบบแล้วดูจำนวนเวอร์ชันที่เกิด | เทียบทุกคอลัมน์ = **14,300 แห่งเปลี่ยนพร้อมกัน** (ปลอมทั้งหมด) เทียบเฉพาะที่รู้ค่าสองฝั่ง = 8,153 แห่งใน 7 ปี และ **643 แห่งระหว่าง มิ.ย. → ก.ค. 2569** ซึ่งเป็นอัตราที่สมเหตุสมผล |

**ผลการตรวจ:** ตรงทุกข้อ และระหว่างตรวจเจอของแถมสองอย่างที่ไม่ได้ตั้งใจหา

   และมีจำนวนแถวเท่ากันคือ 14,693 แถว** (งวดหลังคือการเผยแพร่ซ้ำ ไม่ใช่ข้อมูลใหม่)

   จับคู่ไว้ **คีย์หลัก `(snapshot_date_key, ccn)` จะซ้ำทันทีเมื่อโหลดสองงวดนี้พร้อมกัน**
