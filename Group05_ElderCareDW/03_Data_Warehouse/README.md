## ทำไมต้องมีขั้นนี้ ทั้งที่ ETL เขียนตารางลงฐานข้อมูลไปแล้ว

ETL เขียนด้วย `CREATE OR REPLACE TABLE ... AS SELECT` ซึ่ง**เก็บข้อมูลไว้ แต่ทิ้งข้อสัญญาทั้งหมด**
DuckDB เดาชนิดข้อมูลให้แล้วจบ ไม่มีคีย์หลัก ไม่มีคีย์นอก ไม่มีช่วงค่าที่ยอมรับ

สิ่งที่เอกสารออกแบบรับปากไว้เรื่อง grain คีย์ และช่วงค่า จึงมีอยู่แค่ในโค้ด Python ของ `02_ETL/load.py`
เท่านั้น — และ **assertion ใน Python ไม่ติดไปกับไฟล์ `.duckdb`** ใครก็ตามที่เปิดฐานข้อมูลนี้ใน
notebook ชี้ Streamlit มาที่มัน หรือส่งต่อให้กลุ่มถัดไป จะไม่ได้รับข้อสัญญาเหล่านั้นเลยสักข้อ

ขั้นนี้คือการเขียนข้อสัญญาเดิมลงไปในที่ที่ข้อมูลอยู่จริง `build_warehouse.py` **สร้างไฟล์
ฐานข้อมูลใหม่ขึ้นมาข้าง ๆ ของเดิม** สร้างตารางตาม `schema.sql` ในไฟล์ใหม่นั้น แล้ว**ยัดข้อมูล
เข้าไปผ่านข้อบังคับ** เมื่อสำเร็จจึงสลับไฟล์เข้าที่แบบ atomic — การ insert จึงเป็น
**การทดสอบจริง** ไม่ใช่แค่คำประกาศ

เดิมวิธีนี้แปลงในไฟล์เดิมโดยลบตารางแล้วสร้างใหม่ ซึ่งใช้ไม่ได้: DuckDB ยังจำ
reverse dependency ของคีย์นอกไว้ข้ามลำดับการลบ การลบ dimension จึงถูกปฏิเสธ
เพราะ fact ที่ **ถูกลบไปแล้ว** ยังอ้างถึงอยู่ และความล้มเหลวนั้นทิ้งฐานข้อมูลไว้ครึ่ง ๆ กลาง ๆ
การสร้างข้าง ๆ แล้วสลับตัดปัญหานี้ทิ้งทั้งหมด — ไม่มีอะไรถูกลบ และเมื่อล้มเหลว
ไฟล์เดิมไม่ถูกแตะเลยเพราะไม่เคยถูกเปิดเพื่อเขียน

ต่างจาก `load.validate()` ใน ETL ตรงที่ตัวนั้นตรวจ DataFrame ที่เพิ่งสร้างในหน่วยความจำ
ส่วนตัวนี้ตรวจสิ่งที่อยู่บนดิสก์จริง ซึ่งคือสิ่งที่แดชบอร์ดจะเปิด

### ข้อบังคับใช้งานได้จริง — ตรวจแล้ว

```
INSERT ... facility_key = 88888888  ->  Violates foreign key constraint
UPDATE ... overall_rating = 9       ->  CHECK constraint failed
```

และตอนรันครั้งแรกกับข้อมูลจริง ข้อบังคับ `dim_geography_zip_width` จับได้ทันทีว่าแถว
`geography_key = -1` ถือค่า `'Unknown'` ยาว 7 ตัวอักษร ซึ่ง `verify_dims.py` ยกเว้นไว้อยู่แล้ว
(`WHERE geography_key <> -1`) — สคีมาจึงถูกแก้ให้ยกเว้นแบบเดียวกัน

## Star Schema

```
                    Dim_Date
                   (conformed)
                        |
   Dim_Geography --+----+----+-- Dim_Ownership
                   |         |
        Fact_Facility_Monthly|          Fact_Penalty_Event
        (periodic snapshot)  |          (transaction)
                   |         |                 |
      Dim_Facility-+         +--Dim_Chain      +--Dim_Penalty_Type
        (SCD2)
```

### การประกาศ Grain

| ตาราง | หนึ่งแถวคือ | คีย์หลัก |
|---|---|---|
| `Fact_Facility_Monthly` | สถานที่หนึ่งแห่ง ณ Processing Date หนึ่งงวด | `(snapshot_date_key, ccn)` |
| `Fact_Penalty_Event` | บทลงโทษหนึ่งครั้ง ต่อสถานที่ ต่อวันที่ | `penalty_event_key` |
| `Ref_State_Population` | ประชากร 65+ ของรัฐหนึ่ง ในปีหนึ่ง | `(state_code, year)` |

`Ref_State_Population` **ไม่ใช่ dimension** ไม่มี fact ไหนมีคีย์นอกชี้มา และไม่มีการ join
ด้วยคีย์แทน — เป็นตารางอ้างอิงที่ `v_market_saturation` join ด้วย `state_code`
grain ของมันเองคือสิ่งที่กันไม่ให้ผิด: ถ้าเขียนลง `Dim_Geography` ซึ่งอยู่ที่ระดับ
(ZIP, เมือง, รัฐ) ประชากรของรัฐจะซ้ำทุกแถว ZIP แล้ว `SUM()` จะคูณเกินไปหลายสิบเท่า

**คีย์หลักของ Fact 1 ใช้ `ccn` ไม่ใช่ `facility_key`** — `facility_key` เป็นคีย์แทนของ SCD2
สถานที่เดียวจึงถืออยู่หลายค่า ถ้าประกาศคีย์บนมัน ระบบจะยอมรับสองแถวของสถานที่เดียวกัน
ในงวดเดียวกันได้ ขอแค่มีรอยต่อเวอร์ชันคั่นอยู่ ซึ่งคือแถวซ้ำที่ grain ห้ามไว้พอดี
`ccn` คือตัวตนที่อยู่รอดข้ามการเปลี่ยนเวอร์ชัน จึงถูกเก็บเป็น degenerate dimension ด้วยเหตุผลนี้

## ชั้นความหมาย — `views.sql`

**ให้ query จากวิว ไม่ใช่จากตาราง Fact โดยตรง** measure ถูกนิยามครั้งเดียวที่นี่

เหตุผลไม่ใช่ความเป็นระเบียบ แต่เพราะ **3 ใน 10 measure ให้คำตอบผิดถ้าคำนวณแบบตรงไปตรงมา
และคำตอบผิดนั้นดูสมเหตุสมผลพอที่จะรอดไปจนจบการนำเสนอ**

| วิว | ตอบคำถามข้อ |
|---|---|
| `v_facility_monthly` · `v_penalty_event` | วิวแบน join ดาวครบ ไม่รวมยอด — แดชบอร์ดกรองที่นี่ |
| `v_measure_by_state_period` | BQ5, BQ7 |
| `v_measure_by_ownership_period` | BQ2 |
| `v_measure_by_chain_period` | BQ8 |
| `v_penalty_by_state_year` | BQ7 |
| `v_fines_per_resident_day` | M9, BQ6, BQ7 |
| `v_market_saturation` | BQ1, M10 (**ยังติดขัด**) |
| `v_check_ratio_additivity` · `v_warehouse_coverage` | วิวเฝ้าระวัง มีไว้ให้อ่าน ไม่ได้มีไว้ทำกราฟ |

### กับดักที่วิวปิดไว้ให้แล้ว

**M1 อัตราการเข้าพัก — ห้ามเฉลี่ยอัตราส่วน** ต้องเป็น `SUM(residents) / SUM(beds)`
ไม่ใช่ `AVG(residents / beds)` วัดจากข้อมูลจริงในคลัง

| งวด | SUM/SUM (ถูก) | AVG ของอัตราส่วน (ผิด) | ห่างกัน |
|---|---:|---:|---:|
| 2019-01 | 78.98% | 80.69% | +1.72 จุด |
| 2026-06 | 79.52% | 80.65% | +1.12 จุด |
| 2026-07 | 80.24% | 81.25% | +1.00 จุด |

ทั้งสองตัวเลข "ดูเหมือนอัตราการเข้าพัก" เท่ากัน จึงไม่เก็บอัตราส่วนไว้เป็นคอลัมน์ในตาราง Fact เลย
เพราะการเก็บไว้คือการเชิญชวนให้มีคนกด `AVG()` ใส่มัน

**M3/M4 ชั่วโมงพยาบาลและอัตราการลาออก — ต้องถ่วงน้ำหนักด้วย M2** ถ้าใช้ `AVG` เปล่า ๆ
บ้านพัก 20 เตียงจะมีน้ำหนักเสียงเท่ากับบ้านพัก 300 เตียงในการตอบว่า "ชั่วโมงพยาบาลเฉลี่ย" คือเท่าไร

**M9 ค่าปรับต่อวัน-ผู้พักอาศัย — ห้าม join สอง Fact ตรง ๆ** สองตัวเลขอยู่คนละ Fact คนละ grain
ถ้า join ระดับแถว สถานที่ที่โดนปรับ 12 ครั้งจะทำให้จำนวนเตียงและชั่วโมงพยาบาลของมันถูกนับ 12 รอบ
วิวจึงยุบแต่ละฝั่งลงมาที่ระดับ (รัฐ, ปี) **ก่อน** แล้วค่อย join ผลรวมเข้าหากัน — และใช้ `FULL JOIN`
เพื่อให้ปี-รัฐที่มีค่าปรับแต่ไม่มี snapshot ยังมองเห็นได้ ไม่หายเงียบไปกับ inner join

> **อ่านก่อนอ้างอิงตัวเลข M9** ตัวหารสมบูรณ์เท่าที่โหลด snapshot มาเท่านั้น
> ตอนนี้มี 3 งวด (ม.ค. 2562, มิ.ย. 2569, ก.ค. 2569) ดังนั้นวัน-ผู้พักอาศัยของปี 2562
> คือหนึ่งเดือน ไม่ใช่สิบสองเดือน ขณะที่ค่าปรับเป็นของทั้งปี
> **M9 เทียบข้ามรัฐภายในปีเดียวกันได้ แต่เทียบข้ามปีไม่ได้** จนกว่าจะโหลดชุด `--quarterly` ครบ
> คอลัมน์ `periods_loaded` เปิดไว้ให้เห็นช่องโหว่นี้ตลอดเวลา

**`penalty_count` ห้าม SUM รวมสองประเภท** ค่าปรับเป็นเงิน การระงับการจ่ายเงินเป็นวัน
วิวแยกสองอย่างด้วย `CASE` ทุกที่
