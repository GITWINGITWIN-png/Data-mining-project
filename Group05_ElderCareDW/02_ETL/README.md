> · `verify_dims.py` 24/24 · `verify_facts.py` 23/24 (ข้อที่ตกคือการกระทบยอดกับ CMS
> ดูหัวข้อ "สิ่งที่ยังค้าง" ข้อ 3 — **จงใจไม่ผ่อนเกณฑ์**)

## วิธีรัน

```bash
python -m pip install -r requirements.txt

python fetch_snapshots.py --dates 2019-01-17 2026-06-24 2026-07-29 2026-08-06
python run_dims.py          # สร้าง dimension ลง 03_Data_Warehouse/eldercare.duckdb
python run_facts.py         # สร้าง fact (ต้องรัน run_dims.py ก่อน)
python verify_dims.py       # ตรวจ dimension
python verify_facts.py      # ตรวจ fact รวมการกระทบยอดกับคอลัมน์ที่ CMS คำนวณเอง
```

`run_facts.py` อ่าน dimension กลับออกมาจากฐานข้อมูล ไม่ได้สร้างใหม่ในหน่วยความจำ
เพื่อให้คีย์นอกชี้ไปที่คีย์ชุดเดียวกับที่เก็บไว้จริง

**ต้องรัน `run_dims.py` กับ `run_facts.py` คู่กันเสมอ** — คีย์แทน (surrogate key)
ถูกแจกตามลำดับแถว ถ้าสร้าง dimension ใหม่จากชุดงวดที่ต่างไป เลขคีย์จะเลื่อน
แต่ fact ที่เขียนไว้รอบก่อนยังถือเลขชุดเก่า และทุกแถวยัง join ติด — ติดผิดสถานที่
โดยไม่มีอะไรฟ้อง เพราะ `_validate_foreign_keys` เห็นเฉพาะตารางที่สร้างในรอบนั้น
`run_dims.py` จึง **ลบตาราง Fact ทิ้งทุกครั้งที่สำเร็จ** ตารางที่หายไปคือความผิดพลาด
ที่เห็นได้ทันที ต่างจากตารางที่เลขคีย์เลื่อนไปเงียบ ๆ

คำสั่งอื่นของขั้น Extract

```bash
python fetch_snapshots.py --list         # ดูรายการ 88 งวด พร้อมขนาดไฟล์
python fetch_snapshots.py --quarterly    # โหลดรายไตรมาส (~30 งวด) ค่าเริ่มต้น
python fetch_snapshots.py --all          # ครบทุกงวด ~1 GB
python run_dims.py --dates 2026-06-24 2026-07-29 && python run_facts.py --dates 2026-06-24 2026-07-29
```

ปลายทาง A คืน 96 รายการ = 88 รายการชนิด `theme` (งวดจริง) + 8 รายการชนิด
`annual_theme` (ชุดรวมรายปีที่ซ้ำกับงวดจริง) โค้ดกรองเอาเฉพาะ `theme`
ตัวเลข 88 กับ 96 ในเอกสารออกแบบจึงถูกทั้งคู่ แต่คนละความหมาย

รันซ้ำได้เสมอ: งวดที่โหลดแล้วจะถูกข้าม และ dimension ถูกสร้างใหม่ทั้งตารางทุกครั้ง
จึงไม่มีสถานะค้างจากการรันครั้งก่อน

| ไฟล์ | หน้าที่ |

## ภาษาที่ใช้ในโฟลเดอร์นี้

**โค้ดและข้อมูลเป็นภาษาอังกฤษทั้งหมด** — คอมเมนต์ docstring ข้อความที่ print
ข้อความในตารางบันทึกการทำงาน และ **ค่าที่เก็บใน dimension** (`For profit`, `Unknown`,
`Medium (50-99 beds)`, `Urban`, `Post-COVID`) ส่วนเอกสาร `.md` และเอกสารออกแบบยังเป็นภาษาไทย

ข้อยกเว้นเดียวคือคอลัมน์ `month_name_th` ใน `Dim_Date` ที่ยังเก็บชื่อเดือนภาษาไทย
เพราะชื่อคอลัมน์ระบุไว้แบบนั้นในเอกสารออกแบบ และมีไว้เป็นป้ายกำกับบนแดชบอร์ดภาษาไทยโดยตรง

## การตัดสินใจที่ต้องรู้ก่อนแก้โค้ดนี้

**ทุก dimension มีแถว `key = -1` (`Unknown`)** — เอกสารออกแบบระบุไว้เฉพาะ `Dim_Date`
แต่ที่นี่ทำให้ครบทุกตาราง เพื่อให้ตาราง Fact ไม่ต้องปล่อยคีย์นอกเป็นค่าว่าง
(คีย์นอกที่ว่างทำให้แถวหายตอน join แบบเงียบ ๆ)

**`Dim_Chain` แยก `Independent (no chain)` (`chain_key = 0`) ออกจาก `Unknown` (`-1`)** —
สถานที่ในงวดปี 2562 ต้องชี้มาที่ `Unknown` เพราะยุคนั้นไม่มีคอลัมน์เครือเลย
ต่างจากสถานที่ในงวดปี 2569 ที่คอลัมน์ว่างจริง ซึ่งแปลว่ารู้แน่ว่าไม่สังกัดเครือ

**แกนเวลาของ SCD2 คือ `Processing Date` ในไฟล์ ไม่ใช่วันที่ของ ZIP บนเซิร์ฟเวอร์** —
สองค่านี้ไม่ตรงกัน (ZIP ของวันที่ 2026-06-24 มี Processing Date เป็น 2026-06-01)
เลือก Processing Date เพราะภาคผนวกของเอกสารออกแบบจับคู่คอลัมน์นี้ไว้กับ `snapshot_date_key`
ตาราง Fact จึงต้องใช้แกนเดียวกัน ไม่งั้นเงื่อนไข
`effective_date <= วันที่ของ fact < expiry_date` จะหาเวอร์ชันไม่เจอ

**การเทียบใน SCD2 เทียบเฉพาะคอลัมน์ที่รู้ค่าทั้งสองฝั่ง** — ถ้าเดิมไม่รู้ค่าแล้วงวดใหม่รู้
(เช่น `abuse_icon` ที่เพิ่งมีหลังปี 2562) จะเติมลงเวอร์ชันที่เปิดอยู่ ไม่เปิดเวอร์ชันใหม่
เพราะ "จากไม่รู้เป็นรู้" คือข้อมูลมาช้า ไม่ใช่สถานที่เปลี่ยนสถานะ
ถ้าไม่ทำแบบนี้ ตอนข้ามยุค 2562 → 2569 จะเกิดเวอร์ชันปลอมพร้อมกัน **ทุกแห่ง** (14,300 แห่ง)

**ชื่อสถานพยาบาลถูกปรับเป็นตัวพิมพ์ใหญ่ทั้งหมด** (กฎ Q5) เพราะยุค 2562 สะกดตัวพิมพ์ไม่คงที่
ถ้าไม่ปรับ ชื่อเดิมที่เขียนคนละตัวพิมพ์จะถูกนับเป็น "เปลี่ยนชื่อ" ราว 17% ของทุกแห่ง

**งวดที่เผยแพร่ซ้ำถูกยุบเหลืองวดเดียว โดยเก็บฉบับที่เผยแพร่ทีหลัง** — งวด `2026-07-29`
กับ `2026-08-06` มี Processing Date เดียวกันคือ `2026-07-01` ถ้าไม่ยุบ คีย์หลัก
`(snapshot_date_key, ccn)` ของ Fact 1 จะซ้ำทันที เลือกฉบับหลังเพราะเป็นฉบับแก้ไข
(ตรวจแล้วพบว่า CCN `525685` มี `Staffing Rating` เปลี่ยนจาก 1 เป็น 3 ระหว่างสองแฟ้ม)

**`resident_days` (M2) ใช้จำนวนวันของเดือนตาม Processing Date** — เอกสารออกแบบยังไม่ได้
สรุปนิยามของ "จำนวนวันในงวด" และ M2 เป็นตัวถ่วงน้ำหนักของ M1/M3/M4 กับตัวหารของ M9
**ถ้าเปลี่ยนนิยาม ต้องแก้ที่เดียวใน `facts.py` แต่ measure สี่ตัวจะเปลี่ยนตาม**

**การค้นคีย์ SCD2 อยู่ในฟังก์ชันเดียวคือ `facts.lookup_facility_key()`** ตามที่เอกสารออกแบบ
กำหนด และมีกฎเสริมว่า ถ้าข้อเท็จจริงเกิดก่อนเวอร์ชันแรกที่รู้จัก ให้ใช้เวอร์ชันแรกแทน
ไม่ใช่ชี้ไปที่ `Unknown` — ไม่งั้น Fact 2 เกือบทั้งตารางจะชี้ `Unknown` เพราะค่าปรับ
ย้อนไปไกลกว่า snapshot ที่เก่าที่สุดที่โหลดไว้

**คลังข้อมูลเก็บได้มากกว่าแฟ้มงวดใดงวดหนึ่ง** — มีค่าปรับ 393 รายการ มูลค่า $19.6M
ที่ถูกรายงานหลังจากแฟ้มเดือน มิ.ย. เผยแพร่ไปแล้ว (เช่น Fine ID `139504` $23,000
วันที่ 2026-04-15 โผล่ครั้งแรกในแฟ้มเดือน ก.ค.) นี่คือคุณค่าที่แท้จริงของ Fact 2
ตามที่เอกสารออกแบบอ้างไว้ และเป็นเหตุผลที่การกระทบยอดต้องจำกัดชุดรายการให้ตรงงวด
ไม่ใช่จำกัดแค่ช่วงวันที่

## สิ่งที่ยังค้าง

1. **มีเพียง 6 งวดจาก 32 งวดที่มีข้อมูลเครือ** — CMS เพิ่งเพิ่มคอลัมน์ `Chain Name`
   ในรุ่นเดือน 2025-07 แฟ้ม ProviderInfo ของ **26 งวดแรก (2019-01 ถึง 2025-04)
   ไม่มีคอลัมน์เครือเลย** ไม่ว่าจะเป็นยุค 2019, 2020 หรือ 2026 (ตรวจได้จาก
   `etl_run_log` บรรทัด "columns absent, filled with nulls")
   `_chain_key()` จึงชี้ไปที่แถว **"ไม่ทราบ"** ไม่ใช่ **"ไม่สังกัดเครือ"**
   เพราะสองอย่างนี้ไม่เหมือนกัน
   - `Fact_Penalty_Event` เครือเป็น "ไม่ทราบ" **88%** (96,612 จาก 109,700)
     เพราะการยุบซ้ำเก็บ **การพบครั้งแรก** ไว้ และหน้าต่างหมุน 3 ปีทำให้ค่าปรับ
     ส่วนใหญ่ถูกพบครั้งแรกในงวดเก่า
   - `Fact_Facility_Monthly` มีข้อมูลเครือเฉพาะ 6 งวดล่าสุด (2025-07 เป็นต้นไป)
   **BQ8 ทั้งข้อจึงต้องอ่านจากงวดล่าสุดเท่านั้น** ไม่ใช่ตลอดช่วง 2019–2026
2. **นิยามของ M2 ยังไม่ถูกสรุปในเอกสารออกแบบ** — ตอนนี้โค้ดใช้จำนวนวันของเดือน
   ต้องให้กลุ่มตัดสินแล้วแก้เอกสารให้ตรงกับโค้ด
3. **ยอดค่าปรับต่างจากคอลัมน์ของ CMS อยู่ 2 แห่ง** จาก 6,563 แห่ง รวม $4,126
   จาก $459M (0.0009%) เดิมต่างกัน 444 แห่ง $18.5M ก่อนใช้ Fine ID เป็นตัวระบุตัวตน
   ที่เหลือยังหาสาเหตุไม่ได้ **จงใจปล่อยให้ `verify_facts.py` ตกข้อนี้ไว้**
   แทนที่จะผ่อนเกณฑ์ให้ผ่าน — เกณฑ์ที่ถูกปรับจนผ่านไม่ใช่เกณฑ์อีกต่อไป

4. **แหล่ง S3 (VBP) ยังไม่ได้ใช้** — ไฟล์ถูกคลายไว้แล้วในงวด 2026-06-24 แต่ยังไม่มีโค้ดอ่าน
   ข้อสังเกตข้อ 1 ของ AI log รายการที่ 001 เสนอให้แยกเป็น fact ที่สาม (facility × ปีงบประมาณ)
   ซึ่งยังไม่ได้ตัดสินใจ
